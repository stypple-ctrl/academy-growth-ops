## 1. 목적과 결과물

현재 체험판의 기본 업무 흐름을 유지하면서, 확인하지 않은 사실의 저장과 잘못된 인원 집계 및 저장 안내를 바로잡는다. 동시에 어려운 용어와 필터·버튼 표현을 정리한다.

결과물은 다음 네 가지다.

1. 변경 전 소스 복구본과 복구 경로 안내.
2. 아래 다섯 항목이 반영된 체험판.
3. 변경에 필요한 회귀 검사와 실행 결과.
4. 변경 내역, 검증 상태, 남은 제한, 체험 순서를 적은 완료 보고.

## 2. 착수 조건

- 요청자가 이 작업계약서를 승인하거나 이 범위의 구현 착수를 명시적으로 지시한 뒤 시작한다.
- 실행 직전 현재 파일과 기존 변경사항을 확인한다. 예상과 다른 변경이 있으면 이를 보존하고 영향을 판단한다.
- 보조 에이전트·외부 모델·모델 상향 없이 현재 에이전트가 구현 및 별도 후속 검토를 수행한다.
- 실제 학생 데이터와 외부 서비스는 사용하지 않는다.

## 3. 작업 범위와 인수 기준

### 준비: 현재 버전 보존

- 변경할 앱·테스트·안내 파일을 복구 가능한 형태로 보존한다. 기존 Git 저장소가 있으면 사용자 변경을 먼저 확인하고, 없으면 시각을 포함한 별도 백업 디렉터리에 복사한다.
- 기존 핵심 검사 결과를 확인한다. 기존 실패가 있으면 이번 변경으로 생긴 실패와 구분해 기록한다.
- 브라우저의 기존 저장 데이터를 초기화하거나 데모 버전을 변경해 강제로 새 데이터로 대체하지 않는다.
- 소스 복구본과 브라우저 데이터 백업은 다르다. 소스 백업만으로 브라우저 데이터 복구가 가능하다고 표현하지 않는다.

인수 기준: 변경 전 소스의 위치와 복구 방법을 안내할 수 있고, 기존 브라우저 데이터를 유지한다.

### A. 조교 미확인 기본값 수정

현재 문제: 조교가 확인하지 않아도 ‘혼자 수행·원활’이 기본값으로 저장될 수 있다.

작업:
- 도움 정도와 진행 상태의 첫 표시를 ‘미확인’으로 바꾼다.
- 선택하지 않은 값은 관찰한 사실로 저장하지 않는다.
- 한 항목만 선택하면 선택한 사실만 기록한다.
- 과제 결과 저장을 위해 두 관찰 항목의 선택을 강요하지 않는다.
- 과거에 저장된 관찰은 확인 여부를 역으로 추정해 일괄 변경하지 않는다.

인수 기준:
- 미선택 상태에서 결과 저장 → ‘혼자 수행’이나 ‘원활’이라는 허위 기본 기록 없음.
- ‘1~2회 도움’만 선택 → 그 사실만 기록됨.
- 실제로 ‘혼자 수행·원활’을 선택 → 선택한 내용이 유지됨.

### B. 학생 수와 과제 수 분리

현재 문제: 과제 카드 개수를 학생 인원으로 표시해 중복 인원이 생길 수 있다.

작업:
- 인원 지표는 동일 학생 ID를 한 번만 집계한다.
- 과제 건수와 완료율은 과제 단위를 유지한다.
- 교사·반·학교·학년 필터가 적용된 동일 대상 집합에서 계산한다.
- 과제 중복 등록을 막는 기능은 이번 범위에 포함하지 않는다.

인수 기준:
- 학생 A의 과제 2건 + 학생 B의 과제 1건 → 2명 / 3건.
- 그중 1건 완료 → 과제 완료율은 1/3 기준이며 학생 완료율로 표현하지 않음.
- 대상이 0건 → NaN·Infinity·잘못된 완료율 표시 없음.

### C. 사용자 용어 정리

작업:
- 사용자 화면의 Primary Task → ‘기본 과제’.
- Secondary Task → ‘추가 과제’.
- OPEN의 사용자 표시 → 맥락에 맞는 ‘미해결’.
- 관련 버튼·안내·결과 메시지의 같은 의미 표현을 일관되게 변경한다.
- 데이터의 내부 상태값·키·과제 전환 규칙은 변경하지 않는다.
- 기타 영어 표현 전체 번역이나 디자인 전면 변경은 하지 않는다.

인수 기준: 같은 과제 단계가 화면마다 다른 명칭으로 보이지 않고, 기존 과제 전환과 저장 데이터 호환성이 유지됨.

### D. 필터 범위 및 버튼 동작 설명 정리

작업:
- 기간 필터가 적용되는 기록 영역과 현재 상태 지표를 제목·설명으로 구분한다.
- 현재 상태 지표에 날짜 필터가 적용되는 것처럼 안내하지 않는다.
- ‘반 상세’ 버튼을 실제 이동 목적에 맞는 ‘반 수업 기록’으로 바꾼다.
- 별도 반 상세 화면이나 새로운 기간 집계 로직은 만들지 않는다.

인수 기준:
- 날짜 변경 시 어떤 영역이 바뀌는지 안내만으로 식별 가능.
- 버튼명과 이동 화면의 목적이 일치함.
- 기존 필터 조합과 이동 기능이 유지됨.

### E. 저장 실패 안내 및 입력 보존

현재 문제: 저장 실패 후에도 호출한 동작이 성공 안내·입력 초기화를 실행할 수 있다.

작업:
- 저장 함수에서 성공/실패를 명확히 반환한다.
- 앱 내 저장 호출 지점을 확인하고, 저장 성공에 종속된 메시지·모달 닫기·선택 해제를 성공 시에만 실행한다.
- 실패 시 작성 중인 입력과 선택을 유지하고 저장되지 않았음을 안내한다.
- 데이터 변경 후 저장 실패가 발생하면 저장 전 인메모리 상태로 복구해 재시도 중 사건 중복을 막는다. 현재 입력은 재입력 없이 다시 저장할 수 있도록 유지한다.
- DOM 대체 테스트 환경에서 저장 실패를 주입한다. 사용자 브라우저의 데이터를 삭제해 실패를 만들지 않는다.
- 동시 편집 해결·서버 저장·자동 재시도는 추가하지 않는다.

인수 기준:
- 저장 실패 → 성공 메시지 없음, 입력·선택 유지, 저장 실패 표시.
- 저장 실패 → 대시보드나 타임라인이 미저장 변경을 확정 기록처럼 표시하지 않음.
- 실패 후 정상 저장 재시도 → 해당 기록이 정확히 한 번 저장됨.
- 정상 저장 → 같은 저장소로 앱을 재구성했을 때 변경을 다시 읽을 수 있음.

## 4. 제외 범위

다음은 발견하더라도 이번 단계에서 함께 구현하지 않는다.

- 교사 명단형 입력·빠른 태그·수업 마감·중복 과제 방지.
- 부분완료, 기본/추가 과제 필수 여부, 이월 정책 변경.
- 사용자가 누르는 업무상 되돌리기 버튼과 기록 수정 이력.
- 담당자 배정·조교 인수·교사 결과 확인.
- 새로운 대시보드·반 상세·리포트 개편.
- 학생·반·교사 관리 기능 확대, 타이머 고도화.
- DB·로그인·권한·AI·문자·다른 기기 동기화.
- 데이터 내보내기·복원 기능, 동시 편집 충돌 해결.
- 프로젝트 전체 리팩터링, 프레임워크 이전, 디자인 전면 교체.

저장 실패 직후 내부 상태를 복구하는 것은 E항의 범위다. 저장에 성공한 업무를 나중에 사용자가 취소하는 기능은 제외 범위다.

- test-model.cjs, test-render.cjs: 관련 업무 규칙·화면 회귀 검사.
- README.md: 바뀐 동작과 체험 방법.

예정 추가:

- 단계 완료 보고 문서.

style.css는 바뀐 문구로 인한 잘림 등 좁은 수정이 필요한 경우에만 변경한다. 실행 전 실제 파일 상태를 확인하며, 파일 대분리나 데이터 모델 전면 변경이 필요하면 범위 확대 여부를 먼저 보고한다.

## 6. 실행 순서

1. 변경 전 상태와 기본 검사 결과 보존.
2. A·B의 데이터 정확성 수정과 필요한 회귀 검사.
3. C·D의 표현 수정과 기존 동선 확인.
4. E의 저장 호출 지점 점검, 실패·재시도 처리와 회귀 검사.
5. 관련 검사를 한 번 통합 실행하고 같은 에이전트가 변경 부분을 후속 검토.
6. 가능한 UI 확인과 사용자 체험 안내, 완료 보고.

E항은 저장을 호출하는 여러 동작에 걸칠 수 있어 다섯 항목 중 상대적으로 위험이 크다. 호출 지점별로 확인하고, 다른 단계의 기능을 끼워 넣지 않는다.

## 7. 검증 및 완료 판정

코드 검증:
- 수정한 JavaScript 문법 확인.
- 기존 시험 경계값 23 FAIL / 24 PASS, 추가 과제 전환, 미완료 이월, 공유 기록 필터 유지 확인.
- A·B·E의 인수 기준을 실제 상태 전이와 저장 실패 테스트로 검증.
- 화면 템플릿에서 C·D와 역할별 기존 메뉴가 유지되는지 확인.

실제 UI 검증:
- 데스크탑에서 조교 미확인 상태, 결과 저장, 인원·과제 표시, 기간 설명, 반 수업 기록 이동을 확인한다.
- 필수 작은 화면은 문구·레이아웃 변경으로 영향받는 경우만 확인한다. 스크린샷은 단계당 최대 2회다.
- 현재 저장된 브라우저 접근 차단은 우회하지 않는다. 접근이 허용되면 실제 UI를 확인하고, 그렇지 않으면 사용자에게 체험 확인을 요청한다.

상태는 구분해 보고한다:
1. 구현 완료: 합의한 코드 변경이 끝남.
2. 코드 검증 통과: 관련 자동 검사·후속 검토가 끝남.
3. UI 확인 완료 또는 UI 확인 대기: 실제 확인 여부에 따라 표시.
4. 인수 완료: 합의한 필수 검증과 요청자의 체험 확인이 끝남.

브라우저 확인이 막혀 있으면 ‘전체 검증 완료’나 ‘인수 완료’로 보고하지 않는다. 새 결함이 없으면 이미 통과한 검사를 이유 없이 반복하지 않는다.

## 8. 범위 변경·중단·복구 조건

다음 경우 진행 상황과 남은 범위를 보고하고, 필요한 경우 추가 승인을 기다린다.

- 실제 도구 호출 12회로 승인 범위를 마치기 어려운 경우. 배치 내부 호출도 각각 집계한다.
- 같은 원인의 실패가 최초 시도와 근거 있는 재시도 1회 후에도 해결되지 않은 경우.
- 기존 저장 데이터 삭제·대규모 변환·다른 기능의 동작 변경이 필요한 경우.
- 보조 에이전트, 외부 모델, 모델 상향 또는 이번 계약 밖 기능이 필요한 경우.

원래 있던 범위 밖 문제는 별도로 기록한다. 인수 기준을 막는 문제는 해결에 필요한 최소 범위와 영향을 설명한다. 임의로 전면 수정하지 않는다.

소스 복구가 필요하면 이번 단계 변경만 변경 전 버전과 대조해 되돌린다. 사용자 작업과 기존 데이터를 덮어쓰지 않는다. 브라우저 데이터 복구 기능이 있는 것처럼 안내하지 않는다.

## 9. 비용·작업 방식

- 현재 에이전트 1명, 추가 모델·자동 반복 없이 진행한다.
- 단계의 기본 도구 예산은 실제 호출 12회다. 구현 착수 시 호출 수를 새로 기록하며, 이 문서 작성은 구현 예산과 구분한다.
- 예산 초과 전 완료 항목·남은 작업·예상 추가 호출 수를 보고하고 승인을 받는다.
- 크레딧 차감량과 작업 시간을 확정치로 약속하지 않는다.
- 실제 권한 차단이나 미검증 사항은 완료 보고에 명시한다.

## 10. 완료 보고에 포함할 내용

- 다섯 항목 각각의 변경 결과와 인수 기준 통과 여부.
- 검사 결과 및 실제 UI 확인 여부.
- 기존 브라우저 데이터 보존 여부.
- 백업 위치와 소스 복구 방법.
- 사용자가 확인할 최소 체험 경로.
- 발견했으나 이번 범위에서 고치지 않은 문제.

## 11. 승인 문구

“이 작업계약서의 1단계 범위로 진행해.”

이 승인은 현재 버전 보존과 A~E의 작업에 적용된다. 후속 단계, 실제 서비스 연결, 추가 에이전트, 도구 예산 초과까지 포괄하는 승인은 아니다.
